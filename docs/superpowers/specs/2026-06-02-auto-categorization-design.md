# Авто-категоризация — дизайн

Дата: 2026-06-02
Статус: согласован, готов к планированию реализации

## Контекст

AIFB — дипломный проект (Spring Boot 3.3.5 / Java 21 / PostgreSQL + Flutter Web).
Реализовано: auth, admin, финансовое ядро + цели, семейный бюджет (scope), группы категорий,
лимиты/бюджеты. У транзакции есть текстовая заметка `note`; отдельного поля «продавец» нет.
Авто-категоризации нет.

Цель — **авто-категоризация**: правила «ключевое слово → категория», применяемые при создании
операции (автоматическое распределение) и как подсказка в форме. Третья (последняя) подсистема
scope «D» (группы → лимиты → **авто-категоризация**).

Зависит от ветки `feature/budget-limits` (последняя в цепочке).

## Согласованные решения

- **Форма правила:** `keyword → category`. Совпадение — подстрока в `note` без учёта регистра.
  Цель всегда категория (операции ссылаются на категории).
- **Режим (C):** и авто-присвоение при создании (если категория не указана), и эндпоинт-подсказка
  для формы.
- **Scope (B):** правила **только личные** (персональная привычка пользователя). Семейные правила —
  вне объёма. Авто-присвоение работает только для **личных** операций (`shared=false`);
  семейная операция по-прежнему требует явной категории.
- **Разрешение при нескольких совпадениях:** выигрывает **самое специфичное** правило — наибольшая
  длина `keyword`; при равенстве — более новое (по `created_at`). Учитываются только правила,
  чья категория совпадает по типу с операцией (`category.type == request.type`).

## Модель данных (миграция V12)

### `categorization_rules` (новая)
| поле | тип | примечание |
|---|---|---|
| id | UUID PK | |
| user_id | UUID NOT NULL FK→users ON DELETE CASCADE | владелец (правила личные) |
| keyword | VARCHAR(80) NOT NULL | ключевое слово (матчится без регистра) |
| category_id | UUID NOT NULL FK→categories ON DELETE CASCADE | целевая категория |
| created_at, updated_at, version | | аудит |

- Уникальный индекс `(user_id, lower(keyword))` — без дублей ключевых слов у пользователя.
- Категория правила при создании/правке должна быть видима пользователю в личном scope
  (системная или его личная) — проверяется в сервисе.

## Backend-модуль `finance/categorization/`

Структура по образцу `finance/group`: `api` / `api/dto` / `domain` / `repository` / `service`.

### Эндпоинты
```
GET    /api/v1/categorization/rules                список правил пользователя
POST   /api/v1/categorization/rules   {keyword, categoryId}
PUT    /api/v1/categorization/rules/{id}  {keyword, categoryId}
DELETE /api/v1/categorization/rules/{id}
POST   /api/v1/categorization/suggest {note, type}   → {categoryId, categoryName} | data: null
```
- `suggest`: подбирает категорию по правилам пользователя для заданного `note` и `type`
  (личный scope); если совпадений нет — `data: null`.
- CRUD правил: владение по `user_id` (404 для чужого); категория валидируется (видима в личном scope).

### Логика подбора (`CategorizationService.resolve(userId, note, type)` → `Optional<UUID categoryId>`)
- Если `note` пустой → пусто.
- Берём правила пользователя, чья категория имеет тип `type` и `lower(keyword)` входит в `lower(note)`.
- Сортировка: по убыванию длины `keyword`, затем по убыванию `created_at`; берём первую категорию.

### Интеграция в создание операции
- `CreateTransactionRequest.categoryId` становится **необязательным** (`UUID`, без `@NotNull`).
- В `TransactionService.create`:
  - если `categoryId` указан — поведение как сейчас (валидация по scope/типу);
  - если `categoryId` не указан:
    - `shared=false` (личная): вызвать `categorizationService.resolve(userId, note, type)`;
      при совпадении — использовать найденную категорию; иначе `DomainException(VALIDATION_FAILED, "Категория не определена")`.
    - `shared=true` (семейная): `categoryId` обязателен → `DomainException(VALIDATION_FAILED, ...)`
      (авто-категоризация не применяется к семейным операциям).
- Применение правил — только в личном scope: найденная категория валидируется как личная/системная.

## Frontend

Стиль — как в существующих фичах (data: Dio + модели + repo; presentation: Riverpod + страницы).

- **Новая фича `categorization`** (`features/categorization`): data source/repo/провайдеры + экран
  **«Правила»** (`/rules`): список правил (ключевое слово → название категории), создание
  (ключевое слово + выбор категории из личных/системных), удаление.
- **Форма операции:** при заполненной заметке и пустой категории — вызвать `suggest` (по `note`+`type`)
  и предзаполнить выбор категории (с пометкой «подсказка»); пользователь может изменить. Вызов —
  по потере фокуса заметкой или кнопкой «подобрать».
- `rulesProvider` (список правил, без scope — личные).

## Тестирование

- **Backend (Testcontainers):** CRUD правил (личные, 404 на чужое, валидация категории);
  подбор `resolve`/`suggest` (подстрока без регистра, фильтр по типу, «самое длинное слово выигрывает»,
  нет совпадений → пусто); авто-присвоение при создании операции без категории (личная → подобрана;
  нет правил → 400; семейная без категории → 400); указанная категория не перетирается правилами.
- **Frontend (mocktail):** репозиторий правил (list/create/delete, suggest, маппинг, ошибки).

## Вне объёма (фиксируем явно)

- Семейные правила (scope-aware) — правила только личные.
- Регулярные выражения, несколько условий, приоритеты вручную (только «длина keyword»).
- Отдельное поле «продавец»/контрагент у операции — матчим по `note`.
- ML/обучение на истории; массовая ре-категоризация прошлых операций.

## Известные технические заметки

- Нумерация миграций продолжается с V12 (лимиты заняли V11).
- Авто-присвоение применяется только для личных операций; семейные требуют явной категории
  (личные правила указывают на личные/системные категории, несовместимые со scope семьи).
- Изменение `CreateTransactionRequest.categoryId` на необязательный — аддитивно (существующие
  вызовы с категорией работают как прежде); требует обновления тестов, которые рассчитывают на
  обязательность (если такие есть — их нет, `@NotNull` снимается, поведение при наличии категории не меняется).
