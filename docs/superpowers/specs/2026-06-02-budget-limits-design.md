# Лимиты и бюджетирование — дизайн

Дата: 2026-06-02
Статус: согласован, готов к планированию реализации

## Контекст

AIFB — дипломный проект (Spring Boot 3.3.5 / Java 21 / PostgreSQL + Flutter Web).
Реализовано: auth, admin, финансовое ядро + цели, семейный бюджет (scope личное/семейное,
роли OWNER/ADULT/CHILD), группы (папки) категорий. Категории/группы типизированы (INCOME/EXPENSE),
scope-aware. Бюджетов/лимитов нет.

Цель — **лимиты и бюджетирование**: месячный лимит на категорию или группу расходов, прогресс
(потрачено/лимит) и мягкое предупреждение при превышении. Вторая из трёх подсистем scope «D»
(группы → **лимиты** → авто-категоризация).

Зависит от ветки `feature/category-groups` (нужны группы и `categories.group_id`).

## Согласованные решения

- **Цель лимита (A):** либо категория, либо группа (одна цель на лимит). «Потрачено» — сумма
  расходов по категории / по всем категориям группы за текущий месяц.
- **Период (A):** повторяющийся **месячный** лимит — одна сумма на цель, действует каждый
  календарный месяц; «потрачено» считается за текущий месяц и автоматически «обнуляется» с новым
  месяцем (помесячных копий лимита нет). Без управления бюджетом по конкретным месяцам.
- **Только расходы:** лимиты допустимы лишь на EXPENSE-категории/группы (доход не лимитируем).
- **Оповещение (B):** статусы в приложении (`OK` / `WARNING` ≥ 80% / `EXCEEDED` > 100%) с
  прогресс-барами, **плюс** мягкое предупреждение в ответе на создание операции, если трата
  толкнула бюджет к WARNING/EXCEEDED. Операции **не блокируются**. Push/email — вне объёма.
- **Scope/права:** лимит на семейную категорию/группу — права OWNER/ADULT (как семейный контент);
  на личную — владелец. Scope лимита наследуется от цели.

## Модель данных (миграция V11)

### `budget_limits` (новая)
| поле | тип | примечание |
|---|---|---|
| id | UUID PK | |
| user_id | UUID NOT NULL FK→users ON DELETE CASCADE | создатель |
| household_id | UUID NULL FK→households ON DELETE CASCADE | scope лимита (= scope цели); NULL=личный |
| category_id | UUID NULL FK→categories ON DELETE CASCADE | задан, если цель — категория |
| group_id | UUID NULL FK→category_groups ON DELETE CASCADE | задан, если цель — группа |
| amount | NUMERIC(15,2) NOT NULL | CHECK > 0 (месячный лимит) |
| created_at, updated_at, version | | аудит |

Ограничения:
- `CHECK ((category_id IS NULL) <> (group_id IS NULL))` — ровно одна цель.
- Частичный уникальный индекс на `category_id WHERE category_id IS NOT NULL` и на
  `group_id WHERE group_id IS NOT NULL` — один лимит на цель.
- Тип цели (EXPENSE) и согласованность scope (household_id лимита = household_id цели)
  проверяются в сервисе.

## Backend-модуль `finance/budget/`

Структура по образцу `finance/group`: `api` / `api/dto` / `domain` / `repository` / `service`.

### Вычисление «потрачено» (текущий месяц)
- Границы: с 1-го числа текущего месяца по сегодня включительно (`LocalDate.now()` стартует месяц;
  передаётся в запрос как `from`/`to`, чтобы не звать `now()` в нативном SQL).
- CATEGORY-лимит: сумма EXPENSE-транзакций по `category_id` в нужном scope за период.
- GROUP-лимит: сумма EXPENSE-транзакций, чья категория входит в группу (`category.group_id = :groupId`),
  в нужном scope за период.
- Статус: `OK` (< 80%), `WARNING` (80–100% включительно), `EXCEEDED` (> 100%). При `limit = 0`
  не возникает (CHECK > 0). `percentage = round(spent/limit*100, 1)`.

### Эндпоинты
```
GET    /api/v1/budgets?scope=personal|family   список лимитов c {target, amount, spent, percentage, status}
POST   /api/v1/budgets   {targetType: CATEGORY|GROUP, categoryId|groupId, amount, shared}
PUT    /api/v1/budgets/{id}   {amount}
DELETE /api/v1/budgets/{id}
```
- `create`: цель должна быть EXPENSE и видима в выбранном scope; `shared=true` → семейный лимит
  (household_id = семья пользователя; права OWNER/ADULT); проверка отсутствия лимита на эту цель (409).
- `update`/`delete`: владение — личный (по `user_id`) или семейный (членство + OWNER/ADULT); иначе 404/403.
- `list`: PERSONAL → личные лимиты пользователя; FAMILY → лимиты семьи (пусто, если семьи нет).
- В ответе у каждого лимита — имя цели (категории/группы) и тип.

### Предупреждение при создании операции
- В модуле `transaction`: после сохранения EXPENSE-операции сервис спрашивает у бюджет-сервиса
  предупреждения по затронутым целям (лимит на саму категорию + лимит на её группу), в том же scope.
- `TransactionResponse` дополняется необязательным полем `budgetWarnings: List<BudgetWarning>`
  (заполняется только при create; в list/get — null/отсутствует благодаря `non_null`).
  `BudgetWarning{targetType, targetName, amount, spent, percentage, status}` — включается, только если
  `status != OK` после операции.
- Операция всегда сохраняется (мягкое предупреждение, без блокировки).

## Frontend

Стиль — как в существующих фичах (data: Dio + модели + repo; presentation: Riverpod + страницы).

- **Новая фича `budgets`** (`features/budgets`): data source/repo/провайдеры + экран **«Бюджеты»**
  (`/budgets`): список лимитов с прогресс-барами (зелёный/жёлтый/красный по статусу), создание
  (выбор цели — категория или группа, сумма), редактирование суммы, удаление.
- `budgetsProvider(scope)` (параметризуется `Scope`).
- **Форма операции**: после успешного создания, если в ответе есть `budgetWarnings`, показать
  SnackBar/баннер («Вы превысили бюджет „Еда": 1200 / 1000»). `TransactionModel` получает
  опциональное поле `budgetWarnings` (только для разбора ответа create).
- Опционально: карточка бюджетов на дашборде (можно отложить — основной UX на экране «Бюджеты»).

## Тестирование

- **Backend (Testcontainers):** CRUD лимитов (категория/группа, личные/семейные); запрет лимита
  на INCOME-цель и на цель чужого scope; один лимит на цель (409 на дубль); вычисление «потрачено»
  для категории и для группы (только текущий месяц, EXPENSE, нужный scope); пороги статуса
  (OK/WARNING/EXCEEDED); права на семейные лимиты (CHILD → 403); предупреждение в ответе на создание
  операции, толкнувшей бюджет за лимит.
- **Frontend (mocktail):** репозиторий бюджетов (list/create/delete, маппинг, ошибки).

## Вне объёма (фиксируем явно)

- Бюджеты на конкретные месяцы (помесячное управление) и перенос/копирование бюджета.
- Push/email-уведомления (нужна инфраструктура SMTP/push).
- Блокировка операций при превышении (всегда мягкое предупреждение).
- Лимиты на доходы; общий месячный лимит «на всё».
- Авто-категоризация — третья подсистема.

## Известные технические заметки

- Нумерация миграций продолжается с V11 (группы заняли V10).
- Границы месяца вычисляются в Java (`LocalDate`), в SQL передаются как `from`/`to` —
  не вызываем `now()` внутри запросов (консистентно с уже существующими агрегатами статистики).
- Лимиты переиспользуют `HouseholdContextService` (scope + права) и связь категория→группа.
- `TransactionResponse.budgetWarnings` — аддитивное необязательное поле; в list/get не сериализуется
  (`default-property-inclusion: non_null`), существующее поведение не ломается.
