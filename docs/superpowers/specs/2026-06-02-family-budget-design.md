# Семейный бюджет — дизайн

Дата: 2026-06-02
Статус: согласован, готов к планированию реализации

## Контекст

AIFB — дипломный проект (Spring Boot 3.3.5 / Java 21 / PostgreSQL + Flutter Web).
На момент старта реализовано: `auth`, `admin/db`, и финансовое ядро + цели
(`finance/category`, `finance/transaction`, `finance/statistics`, `finance/goal`) —
всё привязано к одному `user_id` (личные финансы). Семейного бюджета нет.

Цель — добавить **семейный бюджет**: общий «котёл» поверх личных финансов,
с участниками, ролями и разграничением прав, плюс семейная аналитика.

Эта работа зависит от ветки `feature/finance-core-and-goals` (финансовое ядро).

## Согласованные решения

- **Модель совместности (B): личное + общее.** У каждого финансового ресурса есть
  признак владения через колонку-дискриминатор `household_id`:
  - `household_id IS NULL` → **личное** (видно только `user_id`);
  - `household_id = X` → **семейное** (видно всем участникам семьи X).
  Без `owner_type`-enum — одна nullable-колонка на сущность.
- **Роли (OWNER ⊃ ADULT ⊃ CHILD).** Матрица прав ниже.
- **Одна семья на пользователя**, вступление **по коду-приглашению** (без email-инфраструктуры).
- **Семейными могут быть все три сущности**: категории, транзакции (с автором `user_id`), цели.
- **Полная семейная аналитика**: summary/by-category/trend по семейным данным + разбивка
  «кто сколько потратил» по участникам + лента семейных операций с автором.
- **Навигация**: переключатель «Личное | Семья» на дашборде + отдельный экран «Семья».
  Формы операции/цели получают тумблер «Личное/Семейное» (по правам).
- **CHILD** может править/удалять **свои** семейные операции (он автор), но не чужие.

## Матрица прав

| Действие | OWNER | ADULT | CHILD |
|---|:--:|:--:|:--:|
| Личные финансы (свои) | ✅ | ✅ | ✅ |
| Просмотр семейного (всё) | ✅ | ✅ | ✅ |
| Добавить свою семейную операцию | ✅ | ✅ | ✅ |
| Править/удалять свою семейную операцию | ✅ | ✅ | ✅ |
| Править/удалять чужие семейные операции | ✅ | ✅ | ❌ |
| Семейные категории и цели (CRUD, взносы) | ✅ | ✅ | ❌ |
| Управление участниками (роли, удаление, код) + настройки семьи | ✅ | ❌ | ❌ |

Проверки — на уровне сервиса (по `household_role` и владельцу ресурса):
нарушение прав → `403`; чужой/несуществующий ресурс → `404`.

## Модель данных (миграции V8–V9)

### `households` (V8, новая)
| поле | тип | примечание |
|---|---|---|
| id | UUID PK | |
| name | VARCHAR(120) NOT NULL | |
| owner_user_id | UUID NOT NULL FK→users | текущий владелец |
| invite_code | VARCHAR(12) NOT NULL UNIQUE | код вступления |
| created_at, updated_at, version | | аудит |

### `users` (V8, ALTER)
- `household_id UUID NULL FK→households(id)` — семья пользователя (одна или нет).
- `household_role VARCHAR(10) NULL` — `OWNER`/`ADULT`/`CHILD` (CHECK), NULL если не в семье.
- Согласованность: `household_id` и `household_role` либо оба NULL, либо оба заданы.

### `categories`, `transactions`, `goals` (V9, ALTER)
- В каждую: `household_id UUID NULL FK→households(id)`.
- Индекс на `(household_id)` (частичный `WHERE household_id IS NOT NULL`) для семейных выборок.
- Семантика видимости:
  - категории: системные (`user_id NULL, household_id NULL, is_system`) + личные
    (`user_id=me, household_id NULL, deleted_at NULL`) + семейные (`household_id=myHousehold, deleted_at NULL`).
  - транзакции/цели: личные (`user_id=me, household_id NULL`) + семейные (`household_id=myHousehold`).
  - У транзакции `user_id` = автор (для разбивки «кто потратил») всегда.

## Backend-модуль `platform/household/`

Структура по образцу существующих модулей: `api` / `api/dto` / `domain` / `repository` / `service`.

### Эндпоинты
```
POST   /api/v1/households                      создать семью {name}; caller → OWNER (если ещё не в семье)
GET    /api/v1/households/me                    моя семья: {id,name,inviteCode?,members:[{userId,fullName,role}]}
POST   /api/v1/households/join                  {inviteCode} — вступить (роль по умолчанию ADULT)
PUT    /api/v1/households/members/{userId}/role {role} — OWNER; нельзя менять свою роль; второго OWNER нет
DELETE /api/v1/households/members/{userId}      OWNER: удалить участника (его авторские операции остаются в семье)
POST   /api/v1/households/leave                 не-OWNER покидает семью
DELETE /api/v1/households                        OWNER распускает семью (каскад: семейные categories/transactions/goals удаляются)
POST   /api/v1/households/rotate-code           OWNER: перегенерировать invite_code
```
- `inviteCode` в `GET /me` отдаётся только OWNER (остальным — null).
- Удаление участника: его `household_id`/`household_role` обнуляются; семейные операции, где он автор, остаются в семье (`household_id` сохранён, автор — бывший участник).
- Роспуск семьи: каскадное удаление семейных строк через FK `ON DELETE CASCADE` на `household_id` в categories/transactions/goals; у всех членов обнуляются `household_id`/`household_role`.

### Изменения в существующих модулях
- **Списки** `GET /categories|transactions|goals` — добавить `scope=personal|family` (по умолчанию `personal`).
  - `personal`: `household_id IS NULL` и принадлежит пользователю (для категорий — плюс системные).
  - `family`: `household_id = текущая семья пользователя` (если семьи нет — пустой результат).
- **Создание** — в теле опциональный `shared: boolean` (по умолчанию `false`).
  - `shared=true` → `household_id` = семья пользователя (требует членства). Права: категории/цели — OWNER/ADULT; транзакции — любой участник (CHILD тоже).
  - Транзакция при `shared`: тип всё так же должен совпадать с типом выбранной категории; категория должна быть видима в выбранном scope.
- **Правка/удаление** семейного ресурса: проверка прав по матрице (CHILD — только свои операции; категории/цели — OWNER/ADULT).
- **Статистика** — `scope=personal|family` у `summary`/`by-category`/`trend`.
- **Новый** `GET /api/v1/statistics/by-member` (только family) → `[{userId, fullName, income, expense}]`
  — агрегаты по `transactions.user_id` среди семейных операций.

## Frontend (Flutter)

Стиль — как в существующих фичах (data: Dio + модели + repo; presentation: Riverpod + страницы).

- **Новая фича `household`** (`features/household`): data source/repo/провайдеры + **экран «Семья»** (`/family`):
  - нет семьи → «Создать семью» (имя) / «Вступить по коду» (ввод кода);
  - есть семья → список участников с ролями; invite-код (OWNER: показ + перегенерация);
    управление ролями (OWNER); карточка разбивки «кто сколько потратил»; выход (не-OWNER) / роспуск (OWNER).
- **Дашборд**: сегмент-контрол «Личное | Семья» вверху. Провайдеры финансов/статистики
  параметризуются `scope` (FutureProvider.family по scope). В режиме «Семья» добавляется
  карточка «Разбивка по участникам» (из `by-member`); последние операции показывают автора.
- **Формы** операции/цели: тумблер «Личное/Семейное» (включается при наличии семьи и прав;
  для цели у CHILD скрыт). У транзакции при «Семейное» список категорий берётся из семейного scope.
- Маршрут `/family` в `routes.dart` + `app_router.dart`.

## Тестирование

- **Backend (Testcontainers):**
  - Жизненный цикл семьи: создать → вступить по коду → сменить роль → удалить участника → выход → роспуск (каскад).
  - Матрица прав: CHILD не правит чужую семейную операцию (403) и не создаёт семейные категории/цели (403);
    ADULT не управляет участниками (403); OWNER может всё.
  - Изоляция scope: личные данные одного не видны как семейные другому; `scope=family` без семьи → пусто.
  - `by-member`: корректные суммы по авторам.
  - Каскад при роспуске: семейные строки удаляются, личные сохраняются.
- **Frontend (mocktail):** репозиторий household (create/join/me/role/leave) — маппинг и обработка ошибок.

## Вне объёма (фиксируем явно)

- Email-приглашения и мультисемейность (несколько семей у пользователя).
- CHILD-лимиты/«карманные деньги», контроль трат и уведомления.
- Передача владения (transfer ownership) — пока только роспуск семьи OWNER-ом.
- Редизайн под Apple HIG — отдельная тема (следующая спека).

## Известные технические заметки

- Нумерация миграций продолжается с V8 (финансовое ядро заняло V1–V7).
- Каскадное удаление семейных строк завязано на FK `household_id ... ON DELETE CASCADE`.
- `scope=family` требует, чтобы у пользователя был `household_id`; иначе семейные выборки пусты,
  а попытка создать `shared=true` без семьи → `409`/`400` (доменная ошибка).
