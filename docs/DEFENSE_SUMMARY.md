# AIFB — сводка для защиты

**AIFB (AI Family Budget)** — веб-приложение для учёта личных и семейных финансов:
доходы/расходы, категории и статистика, цели накоплений, совместный семейный
бюджет, лимиты с предупреждениями и авто-категоризация операций.

## 1. Архитектура

Клиент-серверное приложение, REST поверх HTTP.

```
Flutter Web (SPA)  ──HTTPS/JSON──►  Spring Boot REST API  ──JDBC──►  PostgreSQL
   Riverpod                          слои: api → service → repository
   go_router                         JWT-аутентификация
   Dio                               Flyway-миграции схемы
```

**Бэкенд** — многослойная модульная архитектура. Каждый модуль: `api`
(контроллер + DTO) → `service` (бизнес-логика, транзакции) → `repository`
(Spring Data JPA) → `domain` (сущности). Единый конверт ответа
`ApiResponse{data, error, meta}`, стабильные коды ошибок (`ErrorCode`),
централизованная обработка через `GlobalExceptionHandler`.

**Фронтенд** — Clean-подобное разделение: `data` (DTO/datasource/repository) →
`domain` → `presentation` (controller/state/page). Состояние — Riverpod,
навигация — go_router (`StatefulShellRoute` с 5 вкладками), сеть — Dio с
интерсепторами (JWT, авто-refresh токена, маппинг ошибок в `Result/Failure`).

## 3. Функциональные модули

- **Аутентификация:** регистрация, вход, JWT-доступ + refresh-токены (ротация,
  обнаружение повторного использования), выход (точечный и со всех устройств),
  **восстановление пароля** (код + новый пароль).
- **Финансовый учёт:** категории (системные + пользовательские), операции
  доход/расход, история, единая валюта.
- **Статистика:** сводка доход/расход/баланс, разбивка по категориям, тренд по
  месяцам, разбивка по участникам семьи — с фильтром по диапазону дат.
- **Цели накоплений:** цели с суммой/сроком, ручные взносы, прогресс и статус
  (ACTIVE/COMPLETED).
- **Семейный бюджет:** семья с кодом-приглашением, роли OWNER/ADULT/CHILD,
  управление участниками, личный и общий (семейный) скоуп для всего контента.
- **Группы категорий** и **лимиты/бюджетирование:** месячные лимиты на
  категорию или группу, статусы OK/WARNING/EXCEEDED (пороги 80% / 100%),
  предупреждения.
- **Авто-категоризация:** правила «ключевое слово → категория», подсказка
  категории по тексту операции.

## 4. Модель данных

13 версионированных миграций Flyway (`V1…V13`), схема применяется автоматически
при старте:

`users`, `user_roles`, `user_settings`, `refresh_tokens` · `categories` ·
`transactions` · `goals`, `goal_contributions` · `households` (+ скоуп
`household_id` на контенте) · `category_groups` · `budget_limits` ·
`categorization_rules` · `password_reset_codes`.

Скоуп контента определяется дискриминатором `household_id` (`NULL` — личное,
заполнено — семейное). Целостность — внешние ключи с `ON DELETE CASCADE/SET NULL`.

## 5. Безопасность

- Пароли — BCrypt; правило: 8–72 символа, минимум буква и цифра.
- JWT access-токен (роли + версия токена) + refresh с ротацией; смена пароля
  поднимает `token_version` и отзывает refresh-токены (инвалидация всех сессий).
- Коды сброса пароля хранятся хешем (BCrypt), TTL, одноразовые; ответ не
  раскрывает, зарегистрирован ли email.
- Доступ к семейному контенту проверяется по членству и роли
  (`HouseholdContextService`).

## 6. Тестирование

- **Backend:** 119 тестов в 27 классах. Интеграционные — на реальной PostgreSQL
  через **Testcontainers** (singleton-контейнер), web-слой — MockMvc.
- **Frontend:** 28 тестов (репозитории/контроллеры на mocktail, виджеты).
- Подход — TDD: для каждой задачи сначала падающий тест, затем реализация.

## 7. Что сделано в рамках работы

Проект принят с нерабочим состоянием (белый экран, ошибки сборки/роутинга,
неполный бэкенд) и доведён до рабочего продукта:

1. Аудит, запуск, исправление сборки и подключения PostgreSQL.
2. Достроено серверное «финансовое ядро»: категории, операции, статистика, цели.
3. Реализован семейный бюджет (роли, приглашения, общий скоуп).
4. Добавлены группы категорий, лимиты/бюджетирование, авто-категоризация.
5. Редизайн интерфейса в стиле Apple HIG.
6. Реализовано восстановление пароля (спека → план → разработка субагентами, TDD).
7. Исправлены дефекты, найденные при отладке:
   - `validateStatus` маскировал 401 → ломал авто-refresh токена;
   - `/statistics/by-member` возвращал 409 вне семьи;
   - **500 в статистике с диапазоном дат** (`:from is null` в JPQL → Postgres не
     выводил тип параметра; обёрнуто в `cast(:from as LocalDate)`);
   - **данные не обновлялись при переключении вкладок** (IndexedStack держит
     страницы живыми) → инвалидация провайдеров вкладки при выборе.

## 8. Ключевые технические решения

- **Единый конверт ответа** и стабильные коды ошибок — клиент переключается по
  коду, а не по тексту.
- **Скоуп через `household_id`** вместо дублирования таблиц — один набор сущностей
  обслуживает личный и семейный режим.
- **Загрузка демо-данных через API, а не SQL-дамп** — системные категории
  создаются с случайными UUID, поэтому переносим только сидер, резолвящий
  категории по имени.
- **Release-бандл фронта статикой** для демо — стабильнее, чем debug-сервер.

## 10. Возможные вопросы

- *Почему JWT + refresh, а не сессии?* — stateless API, горизонтальное
  масштабирование; refresh с ротацией снижает риск кражи токена.
- *Как обеспечивается изоляция данных семьи?* — каждый запрос на семейный контент
  проходит проверку членства/роли; скоуп — параметр `scope` + `household_id`.
- *Почему Flyway?* — версионированная, воспроизводимая схема; БД-агностичная история.
- *Почему Testcontainers?* — тесты на настоящей PostgreSQL, а не H2; ловят
  диалект-специфичные ошибки (как баг с типом параметра в статистике).
- *Что из AI реализовано?* — авто-категоризация по правилам (детерминированная
  основа); чат-помощник и рекомендации — направление дальнейшего развития.
